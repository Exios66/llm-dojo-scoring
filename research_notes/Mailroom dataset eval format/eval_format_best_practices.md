# Structuring LLM-Evaluation Datasets: Best Practices as of October 2026

Context for this research: redesigning the "eval format" of an existing document-extraction evaluation dataset (3302 rows; 5 record types: contract, corporate_record, correspondence, insurance_claim, merger_agreement; per-row document text up to 32k chars; nested gt_fields JSON ground truth; train/test split by md5 hash of filename).

## How do leading eval frameworks expect datasets to be structured (fields, chat format, scoring targets, few-shot handling)?

### Takeaway
The de-facto standard row schema across all major frameworks is a flat, per-example record with an **input** (plain string or a chat `messages` array), a **target** (the canonical answer, optionally a list), an optional **id**, and an open **metadata** bag for everything else (provenance, tags, confidence); every framework then layers task-specific rendering (templates/field-mapping) on top rather than baking prompts into the data.

### Cited Findings
- **Inspect AI (UK AISI)** defines the canonical `Sample` as: `input` (required; `str | list[ChatMessage]`), `choices` (optional list[str]), `target` (`str | list[str] | None` — "Ideal target output. May be a literal value or narrative text to be used by a model grader"), `id`, `description` (short statement of what the sample asks), `metadata` (arbitrary dict), plus `sandbox`/`files`/`setup` for agentic setups. Samples without an `id` get auto-incrementing integer ids — an explicit id field is expected in well-formed datasets. — [Inspect Datasets](https://inspect.aisi.org.uk/datasets.html)
- Inspect supports CSV, JSON, JSONL, and Hugging Face natively; datasets whose fields don't match the convention are adapted via `FieldSpec` (e.g., `input="question"`, `target="answer_matching_behavior"`, `id="question_id"`, `metadata=["label_confidence"]`), or a `record_to_sample` function. Inspect explicitly supports **typed metadata** via frozen Pydantic models (`metadata_as()`), read-only by design — i.e., metadata is for provenance/context, not mutable state. — [Inspect Datasets](https://inspect.aisi.org.uk/datasets.html)
- Inspect's chat format: `input` can be a plain string (internally converted to `ChatMessageUser`) or a full `list[ChatMessage]` of `{role, content}` objects — useful for system prompts, pre-seeded assistant turns, and multimodal content. — [Inspect Datasets](https://inspect.aisi.org.uk/datasets.html)
- **lm-evaluation-harness (EleutherAI)** decouples data from prompting entirely: a task YAML points at a HF Hub dataset (`dataset_path`, `dataset_name`, `dataset_kwargs`) plus split names (`training_split`, `validation_split`, `test_split`), and renders prompts with `doc_to_text`, `doc_to_target`, `doc_to_choice` — each can be a bare column name, a Jinja2 template (e.g. `"{{passage}}\nQuestion: {{question}}?\nAnswer:"`), or a `!function` Python callable. — [lm-eval new_task_guide.md](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/new_task_guide.md)
- lm-eval few-shot handling: `fewshot_split` names the split to draw examples from, or `fewshot_config` hardcodes samples (`sampler: default|first_n`, `samples: [...]`) with optional overrides of `doc_to_text`/`doc_to_target`/`doc_to_choice` **for few-shot examples only** — i.e., the framework assumes few-shot exemplars live in a dedicated split or inline config, not in the test rows. A strict convention: `target_delimiter` (default `" "`) is inserted between `doc_to_text(doc)` and `doc_to_target(doc)`; prompts/targets must not carry trailing/leading whitespace. — [lm-eval new_task_guide.md](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/new_task_guide.md)
- lm-eval supports local datasets via `dataset_path: json` + `dataset_kwargs: {data_files: ...}` and dataset shaping via `process_docs` (`!function utils.process_docs`), so raw datasets are expected to keep near-raw fields and let the harness transform them. — [lm-eval new_task_guide.md](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/new_task_guide.md)
- lm-eval versioning is enforced at task level: every task YAML carries `metadata: {version: N}`, bumped by 1 on any breaking change, with a changelog entry (date, PR number, version delta, one-line description) in the task README. Group configs aggregate subtask metrics with `aggregate_metric_list` (`aggregation: mean`, `weight_by_size: true/false` for micro vs macro averaging) — relevant precedent for scoring across your 5 record types. — [lm-eval new_task_guide.md](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/new_task_guide.md)
- **OpenAI Evals / simple-evals**: OpenAI's platform evals consume **JSONL** files where each JSON object is one sample with prompt/message content and an expected answer or grading rubric; the open-source `evals` registry similarly uses JSONL with `input` and `ideal` fields ("Each JSON object will represent one data point in your eval"). — [OpenAI evals guide](https://developers.openai.com/api/docs/guides/evals); [evals build-eval.md](https://github.com/openai/evals/blob/main/docs/build-eval.md)
- OpenAI's structured-extraction eval cookbook pattern: define clear **tool schemas** for the extraction, run the model against JSONL test data, and grade with rigorous rubrics (exact/semantic checks against expected structured output) — evidence that JSON-schema-bounded output + structured graders is the standard for extraction evals. — [openai-cookbook tools-evaluation.ipynb](https://github.com/openai/openai-cookbook/blob/main/examples/evaluation/use-cases/tools-evaluation.ipynb)
- **HELM (Stanford CRFM)** uses a three-layer abstraction: a `Scenario` "specifies a set of `Instance`s, where each `Instance` has an `input`" and a set of `references` (the gold answers); each scenario is a Python class that reads the raw corpus and emits instances, again keeping prompts out of the stored data. — [HELM code structure](https://crfm-helm.readthedocs.io/en/latest/code/); [HELM Lite](https://crfm.stanford.edu/2023/12/19/helm-lite.html)
- HELM's **legal_support** scenario is a directly analogous document-grounded extraction eval: instances are built from legal citation documents where the model must identify which retrieved passages support a claim — instances carry the source document plus references, with a custom metric. — [legal_support_scenario.py](https://github.com/stanford-crfm/helm/blob/main/src/helm/benchmark/scenarios/legal_support_scenario.py)
- Cross-framework common denominator (synthesis of the above): `input` / `target` / `id` / `metadata` columns, optional `messages` arrays for chat format, prompts and few-shot exemplars kept in task configs rather than in the dataset rows, and per-task YAML/config declaring dataset path, splits, and metric list.

### Inferences
- For the mailroom dataset, the highest-compatibility design is: keep raw document text and ground-truth fields as plain named columns/fields (e.g., `document_text`, `gt_fields`, `record_type`, `id`), and implement any prompt rendering (system prompt, extraction schema, few-shot exemplars) in the harness/task config layer — matching Inspect's `FieldSpec`/`record_to_sample` and lm-eval's `process_docs` pattern rather than pre-rendering prompts into rows.
- Nesting the ground truth as a structured object (JSON) in `target` is compatible with modern practice (OpenAI structured extraction grading, Inspect's `str | list[str]` target, model-graded scorers that take "narrative text to be used by a model grader"), but the row should also expose an `id` and a metadata bag for per-row provenance (source, annotation method, review status) since Inspect treats metadata as the typed/read-only place for exactly that.

### Gaps
- Hugging Face's own first-party eval tooling (e.g., lighteval, lm-eval integration in the `evaluate` ecosystem) has its own task-schema details; I did not fetch its docs within the call budget. Directionally it follows the same HF-dataset + task-config pattern as lm-evaluation-harness.
- No single published spec documents "de-facto conventions" explicitly — the convention claims above are synthesized from each framework's docs, not from a standards document.

## Hugging Face Hub storage layout, dataset cards, and viewer compatibility

### Takeaway
Best practice on the Hub is **Parquet-backed configs declared in README.yaml** (`configs` → `data_files` → `split` → `path`), a dataset card with the full YAML metadata block (license, task_categories, size_categories, source datasets, etc.), data in dedicated split directories or `train-00000-of-00001.parquet`-style shard names, and a SHA content manifest alongside; the viewer auto-converts non-Parquet data into a `refs/convert/parquet` branch.

### Cited Findings
- Supported auto-loadable formats include `.txt`, `.csv`, `.parquet`, `.jsonl`, images, audio, and zip; a correct structure yields automatic `load_dataset()` support and a dataset viewer on the Hub page. — [Repository structure](https://huggingface.co/docs/datasets/en/repository_structure)
- Splits and subsets are declared in the README.md YAML header via `configs: - config_name: default, data_files: - split: train, path: "data.csv"`; `config_name` is **required even for a single config**; multiple files per split and glob patterns are supported; a `default: true` config is loaded when no config is named. — [Repository structure](https://huggingface.co/docs/datasets/en/repository_structure); [Manual configuration](https://huggingface.co/docs/hub/en/datasets-manual-configuration)
- Automatic split detection order (no YAML needed): `train/`/`test/`/`validation/` directory names → delimited filename keywords (`test-file.csv`, `my_train_file.csv`; keywords `train|training`, `validation|valid|val|dev`, `test|testing|eval|evaluation` are equivalent) → custom `-xxxxx-of-xxxxx` shard naming → fallback: everything becomes one `train` split. — [Repository structure](https://huggingface.co/docs/datasets/en/repository_structure)
- Dataset cards: each dataset "should have a dataset card"; creation flow is a README.md with a YAML metadata block (license, language, pretty_name, task_categories, size_categories) that powers Hub discovery/filtering, plus a template with sections (dataset description, sources, collection process, annotation process, considerations) where incomplete fields are filled with `[More Information Needed]`. YAML in the card also customizes loading (splits/configs) without code. — [Create a dataset card](https://huggingface.co/docs/datasets/en/dataset_card)
- **Parquet vs JSONL**: HF's upload guide recommends "Use Parquet format when possible (best compression, rich typing, large dataset support). For smaller datasets (<several GB), JSON / JSONL or CSV are acceptable." — [Dataset upload decision guide](https://huggingface.co/docs/hub/en/datasets-upload-guide-llm)
- The dataset viewer **automatically converts every dataset to Parquet** for performance; when data is already Parquet, no conversion happens and `refs/convert/parquet` files link to the originals. — [Dataset viewer parquet docs](https://huggingface.co/docs/dataset-viewer/en/parquet); [Parquet conversion bot example](https://huggingface.co/datasets/hf-internal-testing/ner-jsonl/discussions/1)
- Viewer/data-studio limits: a restriction applies to datasets **over 5GB** that are not natively Parquet and haven't been auto-converted — natively Parquet datasets avoid the limit. The `refs/convert/parquet` branch is the mechanism DuckDB and others use for efficient remote scanning. — [Data Studio](https://huggingface.co/docs/hub/en/data-studio); [DuckDB + HF docs](https://duckdb.org/docs/lts/core_extensions/httpfs/hugging_face.html)
- Git LFS is the mechanism for large data files on the Hub (implied by all Hub storage guidance; revision/branch usage: the default branch holds the "published" state, and the auto-generated `refs/convert/parquet` branch is tooling-managed and should not be edited).

### Inferences
- For a 3302-row dataset with ~32k-char documents (~roughly 100–300MB of text at most, well under 5GB), either JSONL or Parquet is viewer-compatible; **Parquet is the recommended primary format** (per HF's own guide), with nested `gt_fields` as a Parquet struct/JSON column.
- A split by md5-of-filename can be materialized as two Parquet files (`train-00000-of-00001.parquet`, `test-00000-of-00001.parquet`) in a `data/` directory — the automatic split detector handles it — plus an explicit `configs` block in README.yaml to make the deterministic rule auditable.
- SHA-manifest integrity conventions (per-file sha256/manifest, e.g., a `MANIFEST.sha256` or a provenance JSON with per-file hashes) are community practice rather than a documented HF tooling requirement; the only tooling-managed hash artifact on the Hub is the `refs/convert/parquet` branch and each commit's immutable git SHA (cite: refs/convert/parquet docs above; the manifest convention itself is a gap — see Gaps).

### Gaps
- I found no primary HF documentation specifying a canonical SHA-manifest convention (e.g., required manifest file name/location) for datasets; treat "SHA manifest" as internal/community practice. HF Hub's git commit SHA + LFS pointers are the only first-party integrity mechanisms documented in the pages fetched.
- Exact current (2026) dataset-viewer size/row limits beyond the 5GB non-Parquet rule were not verified.

## Ground-truth labeling conventions for entity/extraction evals (presence/absence, N/A, weights)

### Takeaway
Established extraction benchmarks encode ground truth as **explicit span/value annotations with the presence of a field meaning "found", and absence handled either by omission (field simply not annotated) or by explicit null/negative labels — but the discriminative semantics ("not applicable" vs "verified empty" vs "unlabeled") must be carried by dataset-level documentation or explicit sentinel values, because no framework mandates a shared sentinel vocabulary.

### Cited Findings
- **CUAD** (Contract Understanding Atticus Dataset) is the anchor legal-extraction benchmark: 510 commercial contracts with 13,000+ expert annotations of 41 clause categories. For clause extraction with "associated questions", CUAD "includes the exact substrings (if...)" — i.e., the annotation is the exact text span for each clause when present; when a clause category does not occur in a contract, no span is annotated (the negative case is implicit in the question/answer framing used by downstream evals). — [atticusprojectai.org/cuad](https://www.atticusprojectai.org/cuad/); [ContractEval (arXiv 2508.03080)](https://arxiv.org/html/2508.03080v1); [CUAD NeurIPS D&B paper (Hendrycks et al. 2021)](https://datasets-benchmarks-proceedings.neurips.cc/paper_files/paper/2021/file/6ea9ab1baa0efb9e19094440c317e21b-Paper-round1.pdf)
- **DocRED** (document-level RE/NER over 5,053 Wikipedia documents, 132,375 entities, 56,354 relational facts) encodes entities as structured mentions (position/name/type) and relations as explicit triple instances — presence-based encoding where absence of a triple/entity is implicit, and per-instance ground truth is a machine-readable JSON structure rather than free text. — [thunlp/DocRED GitHub](https://github.com/thunlp/DocRED); [DocRED paper (ACL 2019)](https://aclanthology.org/P19-1074.pdf); [thunlp/docred on HF](https://huggingface.co/datasets/thunlp/docred)
- A 2026 survey of contamination/benchmark-annotation practice (GEM workshop) notes benchmark reliability depends on documented label provenance and that annotation pipelines increasingly record which examples were verified — supporting per-row annotation-method metadata over a single blanket "annotated" flag. — [Nourbakhsh et al., GEM 2026](https://aclanthology.org/2026.gem-main.50/)
- LlamaIndex's extraction-accuracy-benchmarking guidance defines ground truth as "a pre-verified set of expected outputs—manually labeled or otherwise validated" that serves as the reference standard, and treats expected-output absence as a valid test case category (documents where a field is expected to be absent) — i.e., the eval should include both present-field and absent-field cases. — [LlamaIndex extraction accuracy benchmarking](https://www.llamaindex.ai/glossary/extraction-accuracy-benchmarking)
- OpenAI's structured-extraction eval cookbook grades by comparing model structured output against a verified reference answer per field, with grading rules per field — implying per-field scoring granularity (field-level partial credit) is standard rather than all-or-nothing document-level scoring. — [openai-cookbook tools-evaluation.ipynb](https://github.com/openai/openai-cookbook/blob/main/examples/evaluation/use-cases/tools-evaluation.ipynb)
- Data-science versioning literature recommends explicit provenance metadata per dataset/field (who/what/how annotated, when) as FAIR practice — supporting per-field fields like `annotation_method`/`intent_source` in row or card metadata. — [Data Science Journal versioning guidelines (2026)](https://datascience.codata.org/en/articles/10.5334/dsj-2026-037)

### Inferences
- A defensible ground-truth convention for a document-extraction eval: (1) encode present fields as exact values (and, where possible, exact spans) in a structured JSON object; (2) use **explicit distinct sentinels** for the three states — e.g., `"absent"`/null meaning *verified not present in the document*, `null` + an `unverified: true`/`annotation_method` flag meaning *not labeled yet*, and field omission meaning *not applicable to this record type* — because CUAD-style omission-based encoding cannot distinguish these states on its own; (3) document the sentinel vocabulary in the dataset card, since no framework enforces it.
- Per-field scoring weight (some fields matter more) has no standardized encoding in the surveyed frameworks; the practical pattern is to store weights in metadata (per-row or per-field inside the gt object) and implement them in the scorer — consistent with Inspect's metadata-as-typed-config and lm-eval's custom-metric functions.

### Gaps
- I did not find a primary source documenting how CUAD or other NER benchmarks explicitly encode "not applicable vs not labeled vs verified empty" beyond the implicit omission convention; explicitly distinguishing these three states appears to be uncommon in public extraction benchmarks, so any sentinel scheme your dataset adopts is a design decision to document, not a community standard to match.
- No survey of per-field scoring-weight conventions in extraction benchmarks was found within the tool-call budget.

## Split hygiene and contamination

### Takeaway
Best practice in 2026 is deterministic, documented splits with **grouping by source to prevent leakage** (all documents from one source/contract set in one split only), plus active contamination checking of test data against popular training corpora — while acknowledging that no contamination-detection method is reliably effective at scale, which pushes the field toward harder-to-remember, document-grounded, private/rotated test sets.

### Cited Findings
- A 2026 GEM-workshop survey (ACL Anthology) concludes: "Across studies, no detection method is consistently reliable across contamination tiers, model-access settings, and training stages" — so dataset authors should design for contamination resistance (deterministic splits, grouping, published split hashes) rather than rely on post-hoc detection alone. — [Nourbakhsh et al., GEM 2026](https://aclanthology.org/2026.gem-main.50/)
- The contamination-detection toolkit itself is well mapped: n-gram overlap, MinHash, embedding similarity, and membership-inference style probes are the standard families; "Awesome Data Contamination" catalogs the detection literature including the Data Contamination Quiz approach and training-time watermarking of benchmark data to enable later detection. — [mbrenndoerfer contamination overview](https://mbrenndoerfer.com/writing/benchmark-contamination-llm-detection-mitigation); [awesome-data-contamination](https://github.com/lyy1994/awesome-data-contamination); [Detecting Benchmark Contamination Through Watermarking (arXiv 2502.17259)](https://arxiv.org/html/2502.17259v2)
- Deterministic splitting from a content hash (like md5 of filename) is a recognized reproducibility pattern; its hygiene requirement is that the rule be **published and re-checkable** (the hash rule and modulo bounds documented in the card) so that adding rows never silently reshuffles the split — this is why frameworks like lm-eval pin exact dataset revisions for reproducibility. — [lm-eval new_task_guide.md](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/new_task_guide.md) (dataset_path/split declarations imply pinned, versioned data); [HF Data Studio](https://huggingface.co/docs/hub/en/data-studio) (immutable refs per revision)
- Practitioner guidance on eval-set construction stresses keeping holdout sets private/unpublished and avoiding duplicate documents across splits as the two highest-leverage hygiene controls for document-grounded evals. — [LlamaIndex extraction accuracy benchmarking](https://www.llamaindex.ai/glossary/extraction-accuracy-benchmarking); [LatentEval contamination check ladder](https://latenteval.ai/research/benchmark-contamination)

### Inferences
- For the mailroom dataset, md5(filename)-based splitting is deterministic and reproducible, but the contamination risk to document in your record is that all rows from the **same organization/thread/source** should land in the same split (group-by-source), because test/train rows sharing a source lets a model pattern-match source-specific templates; the split rule should be upgraded (or at least audited) to group-by-source + hash.
- Recommended: publish the split algorithm and per-split row counts + split-group hashes in the dataset card, and record a run of an overlap check (n-gram/MinHash) of the test split against popular pretraining corpora in the card's contamination section.

### Gaps
- I did not find a framework that *enforces* group-by-source splitting — it is community practice for document-grounded evals, not a tooling requirement, in the sources fetched.
- Quantitative contamination-threshold guidance (what overlap rate is "clean") was seen only on secondary sources (latenteval.ai) without primary backing; treat thresholds as contested.

## Versioning: signaling label revisions and label-audit tooling

### Takeaway
The tooling-enforced mechanism for versioning an eval is a **version field in the eval/task config** (lm-eval: `metadata: {version: N}` + changelog), backed by immutable Hub revisions/branches for draft states; per-field provenance (`annotation_method`, `intent_source`) is FAIR-recommended practice but must be carried in row metadata or card sections, and label-audit/parity checking is done with ad-hoc scripts rather than a dominant standard tool.

### Cited Findings
- lm-evaluation-harness mandates `metadata: {version: N}` per task/group, bumped on every breaking change, with a public changelog line (date, PR, version transition, description) — the clearest tooling-enforced label/definition-revision convention in the surveyed frameworks. — [lm-eval new_task_guide.md](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/new_task_guide.md)
- Hugging Face Hub datasets are git repositories: each commit is an immutable revision; the auto-generated `refs/convert/parquet` branch demonstrates the sanctioned branch-per-purpose pattern — a dataset can keep a `draft` or `v2-labels` branch for label revisions and merge/promote via PRs, with every state addressable by SHA. — [HF Data Studio / refs/convert/parquet](https://huggingface.co/docs/hub/en/data-studio); [DuckDB HF branch scanning](https://duckdb.org/docs/lts/core_extensions/httpfs/hugging_face.html)
- "What Do We Mean by 'Version'?" (Data Science Journal, 2026) provides actionable guidelines distinguishing dataset versions, label/annotation revisions, and schema versions, recommending explicit, separately-versioned identifiers for each — supporting a schema like `dataset_version` + `labels_version` rather than one conflated version number. — [Data Science Journal 2026](https://datascience.codata.org/en/articles/10.5334/dsj-2026-037)
- Standardized versioning frameworks (FAIR-compliant) recommend immutable snapshots with version metadata and provenance records so evaluation runs can be tied to an exact label state. — [González-Cebrián et al., PMC 2024](https://pmc.ncbi.nlm.nih.gov/articles/PMC11003959/)
- Practitioner data-provenance guides (CMU MLIP handbook; Cohere; Voxel51) converge on: record where each record came from, how it was transformed/annotated, and which model/eval consumed it; immutable snapshots (branches or versioned tables) for comparison and audit. — [CMU MLIP versioning chapter](https://mlip-cmu.github.io/book/24-versioning-provenance-and-reproducibility.html); [Cohere provenance blog](https://cohere.com/blog/data-provenance); [Voxel51 3.0 provenance](https://voxel51.com/blog/data-provenance-voxel51-3-0)
- Inspect AI's typed metadata (read-only Pydantic models validated at load) is the closest tooling-level mechanism for per-row provenance fields with validation — fields like `intent_source` or `annotation_method` fit exactly there. — [Inspect Datasets](https://inspect.aisi.org.uk/datasets.html)

### Inferences
- Recommended versioning shape for the mailroom dataset: (a) dataset-level `version` (breaking changes), (b) `labels_version` (label re-annotation waves that don't change rows), (c) per-row provenance (`annotation_method`, `intent_source`, reviewer, review date) inside row metadata, and (d) a git/Hub branch strategy: `main` = published state, `labels-draft` or similar for in-flight revisions, with a SHA manifest per release.
- "Label-audit/parity checks" (re-checking ground truth against source documents, or diffing label revisions across versions) have no standard named tool in the sources fetched — expect to implement a small audit script (e.g., span-verbatim verification of gt_fields values against document_text, plus per-field agreement rates between annotation waves) and version its report alongside the labels.

### Gaps
- No dominant, named open-source "label audit" tool surfaced in the searches; the claim that such checks are custom scripts is based on absence of evidence in search results within the tool-call budget, not a positive citation.

## Long-document (up to 32k chars) extraction evals

### Takeaway
For documents of ~32k characters (well within modern model context windows), the leading practice is to evaluate **full-document prompts** (whole document + structured output schema) rather than chunked prompts, since chunking changes the task and complicates ground-truth alignment; the dataset should store the full text as one field and let the harness own context budgeting, with token-length metadata recorded per row.

### Cited Findings
- Snowflake's finance-RAG study found "**Document context outperforms chunk-level context**" and that choice of chunking can matter more than the generative model — direct evidence that whole-document context yields better extraction than chunked context for finance-style documents. — [Snowflake engineering blog](https://www.snowflake.com/en/blog/engineering-impact-retrieval-chunking-finance-rag/)
- Modern long-context models make full-document embedding/prompting feasible, and chunking is now framed as a retrieval-efficiency tradeoff rather than a necessity: "Late chunking requires embedding the full document at once, which is impossible if the document is longer than the model supports" — i.e., only over-model-length documents force chunking. — [PremAI RAG chunking 2026](https://www.premai.io/blog/rag-chunking-strategies-the-2026-benchmark-guide/); [NVIDIA developer blog on chunking strategies](https://developer.nvidia.com/blog/finding-the-best-chunking-strategy-for-accurate-ai-responses/)
- ~32k characters ≈ roughly 6–10k tokens for typical English text — comfortably below 128k-token default context windows of flagship 2025–2026 models, so full-document prompting is viable; the frameworks' own conventions support this: Inspect `Sample.input` takes a single string (or message list) with no chunking semantics, and lm-eval renders the whole doc into one prompt via `doc_to_text`. — [Inspect Datasets](https://inspect.aisi.org.uk/datasets.html); [lm-eval new_task_guide.md](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/new_task_guide.md)
- Chunking evaluation research (Chroma technical report) evaluates chunking strictly as a retrieval-quality question, separate from extraction accuracy — reinforcing that for an extraction eval, the document should be presented whole and chunking decisions belong to retrieval systems, not to the eval dataset. — [Chroma "Evaluating Chunking Strategies for Retrieval"](https://www.trychroma.com/research/evaluating-chunking)
- Long-context benchmark suites (e.g., SCROLLS, integrated in lm-eval) handle long documents by keeping the entire document in the instance and letting task config manage prompt assembly — the harness-class pattern for long inputs. — [lm-eval new_task_guide.md (scrolls group example)](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/new_task_guide.md)

### Inferences
- For the mailroom dataset: keep full document text (up to 32k chars) as a single `input`/column, record per-row token/char length in metadata (useful for stratified reporting of accuracy vs document length), and design the schema so a harness can optionally apply truncation/chunking policies without changing the data.
- 32k chars is small enough that context budget is a non-issue for current models but a real issue for small/edge models — worth recording `context_tokens` per row and stratifying metrics, since extraction accuracy is known to degrade with input length in many settings (directional claim; primary benchmark citation is a gap below).

### Gaps
- I did not find a 2026 primary study specifically measuring extraction accuracy vs document length in the 8–16k token range within the tool-call budget; the "accuracy degrades with length" inference is directionally supported by the Snowflake/chunking literature but not precisely cited here.
- Whether any major eval framework natively supports per-row context-budget policies (truncation specs in metadata) was not confirmed — the surveyed frameworks all render prompts in task configs, implying policies live there, not in data.
