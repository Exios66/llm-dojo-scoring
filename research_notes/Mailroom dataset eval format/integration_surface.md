## Which code loads the HF dataset or its files, at which pins?

### Takeaway
There are **five distinct load paths, each with its own pin**: (1) llm-mailroom's `pipeline.hf_corpus_loader` (datasets-server `/parquet` HTTP ladder, pin = moving Hub tag `v9.1`), used by eval-environment via editable install; (2) direct `hf_hub_download` of the exact `parquet/{config}/{split}/{split}-00000-of-00001.parquet` shard paths (sandbox `corpus.py`, dojo `verify_gt_penalties.py` / `gen_maud_catalog.py`, each with its own SHA constant); (3) stdlib+/rows fetches inside llm-mailroom scripts; (4) the corpus-producer stack in Mailroom-Corpus-EDA (owns build/publish); (5) mailroom-ML training (its own separate HF repo). Nothing anywhere in Cold_Storage references `ground_truth_hardened.jsonl`, `bundles.jsonl`, or `streams.jsonl` as *files* — every JSONL consumer is the producer-side (EDA build/revision tooling); downstream consumers all go through the parquet **configs** or the viewer API. `corporate-labels-v9` / `corporate-labels-v9.2.1` is **not a file** — it is a **branch on the HF dataset repo** (`refs/heads/corporate-labels-v9.2.1` @ `0a2f8292`), confirmed live.

## How are eval runs built from the dataset, and which columns/keys does each consumer actually read?

### Takeaway
A case built from each corpus row reads a small, stable contract: `filename` (join key + case id), `doc_text` (text), `expected` (doc class), `expected_subclass`, `expected_specialist`, `expected_stage`, `review_expected`/`retry_expected`, and the **`gt_fields` JSON string** (which is degraded into the flat `expected_fields` scoring surface, dropping `cuad_clause_labels`/`maud_clause_labels` as raw material). Provenance/relation columns (`document_id`, `source_corpus`, `matter_id`, `group_id`, `synthetic`, `content_sha256`, `gt_presence`, `intent_source/confidence/status`, `related_document_ids`, `relationships`) ride along as metadata, identity, or never-scored annotation keys. Never positional alignment: default⇆ground_truth are always joined on `filename`.

### Cited Findings

**eval-environment case construction (`evals/cases.py`):**
- `_case_from_row` maps a row → case: `id = f"corpus:{config}:{split}:{filename}"`, `text = row["doc_text"]`, `expected_doc_class = row["expected"]`, `expected_subclass`, `expected_specialist`, `expected_stage`, `_truthy(row["review_expected"])`, `_truthy(row["retry_expected"])`, `expected_fields = _expected_fields(row)`, `source = "mailroom-dataset"`, plus fixture columns (`fixture_kind`, `calibration_cell`, `probes_confidence`, `failure_stage`, `arbiter_outcome`, `failure_note`, `arbiter_note`, `review_reason`, `expected_correction`, `expected_post_retry_state`, `expected_post_correction_state` — `FIXTURE_FIELDS`, cases.py:57-69) and `case["row"] = {document_id, source_corpus, matter_id, group_id, synthetic}` where non-empty — [cases.py:229-259]
- `_expected_fields` parses the **`gt_fields`** label JSON and flattens it via `evals.extraction_scope.applicable_expected_fields(...)`; raw `cuad_clause_labels`/`maud_clause_labels` are popped (source material only) — [cases.py:196-226]; `INSURANCE_GT_FIELDS` enumerates the 13 claim fields whose names are scored — [cases.py:40-54]
- Guard rails: v9 GT emptiness tokens `'{}'`/`'[]'`, `numpy.ndarray` from frame→records, and `is_empty_gt/is_missing_scalar` handling — [cases.py:113-125]
- `dojo_wiring.py` re-derives the taxonomy from the corpus ground_truth frames ("doc_classes → field_types maps") and warns that "unknown fields are scored as 0" — [src/evals/dojo_wiring.py:11-187](src/evals/dojo_wiring.py)

**llm-dojo-scoring scoring-side column contract:**
- `gt_metadata.parse_gt_fields` / `scoring_gt_fields` are the ONLY door from Hub GT into scoring: `gt_fields` is a JSON string containing the union of all classes' fields + a stringified `gt_presence` map; presence statuses `populated | not_applicable | schema_documented_absence | pending_annotation` are always scored as empty; `ANNOTATION_KEYS` — never extraction targets — includes `gt_presence`, `cuad_clause_labels`, `intent_status`, `intent_source`, `intent_confidence`, `label_evidence`, `topic_evidence`, `sentiment_evidence`, `sentiment_score`, `context_window_band`, `token_estimate`, `clause_count`, `maud_label_count`, `related_document_ids`, `relationships`, `expected_subclass` — [llm_dojo_scoring/gt_metadata.py:1-90](llm_dojo_scoring/gt_metadata.py)
- The "Hub row" contract in code (verified tests/verify script): columns read are `expected`, `expected_specialist`, `gt_fields`, `doc_text` (for scoring inputs); MAUD answer classes from `gt_fields.maud_clause_labels[*].valid_classes` — [scripts/verify_gt_penalties.py:164-192], [scripts/gen_maud_catalog.py:291]
- `corpus.py` is the taxonomy SSOT pinned by docstring to the published merge (class → subclass vocabulary, extraction fields, differentiators; correspondence enum set to exactly the v9 GT `expected_subclass` tokens, `DME-071: the dataset pin is the source of truth`) — [llm_dojo_scoring/corpus.py:1-120]
- PR branch additions: per-subclass **corporate_record** schemas + **unlabeled-GT-aware scoring** (`unlabeled_fields(...)` per row, `entity_unlabeled:<field>` audit codes) because published v9 GT labels none of `entity_name`/`record_type`/`effective_date`/`signatories`/`jurisdiction`/`filing_number` on the 450 corporate_record rows — [llm_dojo_scoring/corporate_record_schema.py:22](llm_dojo_scoring/corporate_record_schema.py), tests [tests/test_corporate_record_schema.py:101-157]
- `scripts/relabel_corporate_record_gt.py` + `corporate_record_relabel.relabel_row` **produce** a repaired GT proposal in the exact row JSON shape (rewrites `gt_fields`, keeps `expected`, `expected_subclass`, per docs "Review the JSONL, then push to the Hub") — [scripts/relabel_corporate_record_gt.py:1-49], CHANGELOG diff confirms the v9.2 audit basis.

**local-mailroom-sandbox row normalization:**
- `normalize_rows` is the canonical `dataset.jsonl` row shape: id (`document_id`/`filename`), `filename`, `doc_text` (+ aliases `expected_doc_class`/`doc_type`, `text`), verified-or-filled `content_sha256` (checked against `sha256(doc_text)`; mismatch raises), **`gt_fields` → `expected_fields`** (JSON string decoded, never silently `{}`), `expected_subclass`, … — [local-mailroom-sandbox/src/mailroom_sandbox/corpus.py:215-259]
- Stratification/sampling also reads `expected_subclass` (strata keys, `expected_doc_class::expected_subclass` key) — [corpus.py:296-397,708]
- `eval/extraction_scope.py:128` excludes `intent_source`/`intent_confidence`/`intent_status` from the scored surface (they are provenance columns, not extraction targets).

**crew/EDA-side contract (frames the shape):**
- `eval_contract.py` derives `expected_specialist` (from llm-mailroom `taxonomy.yaml`), `expected_stage` (`archived/review/failed`), `review_expected`, `retry_expected`, `annotation_provenance` (§43; from existing columns `intent_source` → regime) — [src/mailroom_eda/eval_contract.py:1-70]; the `ground_truth`-config column lists incl. `expected/expected_subclass/split` in [src/mailroom_eda/hardened.py:53-59]
- `matter.py` writes relations: `related_document_ids` as JSON arrays and `gt_fields.related_document_ids` mirror copies — [src/mailroom_eda/matter.py:152-304]; v9_2 revision made `related_document_ids` producer+mirror SSOT and nests `intent_source` inside `gt_fields` — [src/mailroom_eda/v9_2_revision.py:13-40]

### Inferences
- The practical format contract downstream is: **five configs, join key `filename`, blind config fields `filename/doc_text/prompt/metadata`, GT config carrying (at minimum) `filename`, `expected`, `expected_subclass`, `expected_specialist`, `expected_stage`, `review/retry` expectations, `document_id`, `content_sha256`, stringified `gt_fields` (JSON with `gt_presence` inside), `split`** = `train|test`, splitrule `md5(filename)%10==0→test`. Anything else is text or metadata read only by §120/measurements or producers.
- Because every consumer factors through `expected_fields` flattening from `gt_fields`, a format change that moves labels out of `gt_fields` (or re-names the column) breaks ALL of: eval-environment `_expected_fields`, sandbox `normalize_rows`, dojo `parse_gt_fields`, `verify_gt_penalties`, `audit_corporate_record_labels`/`relabel`.
- The dataset semantics "blind never has labels" is enforced in two places (sandbox refuses `ground_truth`-missing loads; card language) — a new spread-format config must be either GT-carrying or explicitly non-eval.

### Gaps
- Whether the eval-environment *scoring* suite reads `related_document_ids`/`relationships` for scoring beyond exclusion (I confirmed exclusion only) — not fully traced per metric.
- The `pilot`/`enron`/`claims` family corpora's exact column expectations were not traced in depth (only the load path) — they are separate HF repos, out of scope for mailroom-dataset format change.

## How do results flow to Braintrust / Langfuse and where is the experiment log published? Which identifiers tie runs to dataset revisions?

### Takeaway
Provenance is threaded as **explicit provenance keys** — most importantly `dataset_revision`, in three namespaced places: (a) dojo Emitter requires it (and prompt_id/serving_kind/model_id) on every score (and refuses scoring without it); (b) sandbox accepts/shapes `dataset_revision` and validates it as a full 40-hex Hub sha; (c) Braintrust rows have `hf_repo` / `hf_revision` metadata (E anomaly: build name `mailroom-hf-<8-sha>`), and the experiment log's `dataset` object carries repo/revision/subset. Publish targets: `reports/experiment_log.jsonl` + `.md` (repo) + `reports/experiment_log/<run>/` + `data/experiments/<run>` dirs + the Vercel viewer `web/data/snapshot.json` (`export_site_snapshot.py`) — with `experiment-log-sync` agents (sandbox/eval-environment subagent rosters) syncing Braintrust/Langfuse runs into the log and publishing to a `gh-pages` branch / reports site (mailroom-issues site is served from `gh-pages:/docs`).

### Cited Findings
- Emitter provenance contract: `EMIT_REQUIRED_PROVENANCE` = `("dataset_revision", "prompt_id", "serving_kind", "model_id")` (emitter.py:229-267); example `provenance={"dataset_revision": "46a4d3c2", "prompt_id": "sorter_v3", ...}` and the scorecard keys (emitter.py:19); local manifest sink JSONL always available. **Note**: the docstring example hard-codes the *old* v9 GT-closure SHA `46a4d3c2` while the current pin is v9.2 — proving the constant is just illustrative (not a pin on the value) — [llm_dojo_scoring/emitter.py:16-70,229-267]
